# 反馈分级：A 亲历 / B 直接观察 / C 推断

写 bug 记录、写 profile 反馈、在对话里说“实测”之前，先给这条信息定级。**级别决定它能不能推动改动。**

## 三级

| 级 | 定义 | 例子 | 能用来干什么 |
|---|---|---|---|
| **A 亲历** | 自己跑出过命令与输出 | “`node Script\verify.mjs` 返回 exit 1，末行是 …” | 直接改、直接加回归 |
| **B 直接观察** | 看到文件/日志/源码，但没亲手复跑 | “`FACTS.md:44` 写着 VERIFY 路径，该文件不存在” | 合并去重后改；改完要补 A 级复跑 |
| **C 推断** | 根据命名、经验、相似项目猜的 | “估计是 janino 不支持新版语法” | 只当线索；**不得写成“实测”**，不得单独据此改代码 |

## 写法模板

```markdown
### 现象（A）
命令：`node Script\<脚本> …`（具体命令见 `INDEX.md` 命令段）
输出：`…`（exit N）

### 证据（B）
`文件:行`：原文摘录

### 推断（C）
可能是 ……（未复跑，待 A 级验证）

### 建议
……
```

## 硬规则

1. 每条反馈必须标级；没标级按 C 处理。
2. C 级不得出现在验收证据里；验收只认 A。
3. “之前有人说/文档写着”属于 B，不是 A。
4. 同一现象有 A 级证据时，旧的 B/C 条目直接合并，不重复计数。
5. 归因先排除 DSH 边界（`pwsh` 参数、审批、ACL），再算 skill 缺陷。

## 收敛规则

P0/P1/P5 验收完成后，**只处理新的 A 类证据**；B 类合并去重后集中处理；C 类不排期。

这条是为了避免“每轮都从旧推断重新开始”，把注意力留给可复现的问题。
