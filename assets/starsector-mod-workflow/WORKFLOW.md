# Moci 开发流程

入口与约束见 SKILL.md；环境事实见 REF/moci-environment.md。

## 选择工作量

- 改数据、修一个方法、修文本：读附近工作样例，直接改，运行相关检查。
- 涉及多类协作、状态机、存档或 UI：先明确行为与验收。必要时在 docs/ 写短设计，再按模块推进。
- 大功能：按可验证的阶段实现。只就影响数值、交互或发布范围的真实歧义询问用户。

流程文档是辅助，不强制用户反复审批。不要为普通小修改创建审批哈希或为通过闸门而补形式化测试。

## 找到正确的文件

1. 从工程 WORKSPACE.md 确认 src、MociShipPack 和参考 mod 的角色。
2. Java 类同时查 src、MociShipPack/data 与 com；原版源码另查绑定游戏 starsector-core/data。按 package 和顶层类声明识别，修改时保留原位置。CSV、配置和贴图在 MociShipPack 中查找。
3. 验证 API 时先查本地源码和绑定依赖。不要把旧作者环境的行号、版本、mod 路径直接迁入本工程。
4. 机体配置与剧情任务分别结合已有两个专项 skill。

势力音乐任务按 [REF/moci-faction-music.md](REF/moci-faction-music.md) 同时查 faction 音乐映射、sounds.json 曲库登记与音频资源。先在 MociShipPack 中完成主题、市场/舰队交互、战斗分配与验证，再展示具体清单，询问是否同步游戏。

编写或修改每帧回调、范围搜索和批量实体处理时，按 [REF/moci-performance.md](REF/moci-performance.md) 选择查询与更新方式。先核对 Moci_Util 中实际使用的 Grid/全场扫描实现，再处理平方距离、重复除法、对象分配与缓存；小修只检查相关路径，不扩大为全工程优化。

遇到战斗卡死、窗口未响应或只有某些 mod 组合才出现的长停顿时，追加一次数值边界审计：检查质量/转动惯量等除数是否极小但非零，检查力矩或角加速度是否溢出，并检查传给 `setFacing` 等引擎入口的角度是否有限且已归一化。先读当前绑定版本的引擎实现；`setFacing` 的归一化周期可能是 180、360 或其他值，风险在于无上限重复减法，而不是某个固定常数。不要把没有异常日志当作性能问题的证据；优先在复现期间采集 JFR 或 JVM 线程栈，确认主线程是否反复执行无上限的角度/数值归一化循环，再用禁用 mod 的二分法和原始数值日志定位来源。相关代码不得新增无上限的重复加减循环，角度归一化应使用常数时间运算或带上限的降级路径。

## 工具与验证

从 skill 根运行 node Script/moci.mjs <命令>，或从工程目录用脚本绝对路径。

- doctor 检查绑定与工具可用性，不表示编译或游戏运行已通过。
- compile 用 JDK 17 执行 Maven compile，仅覆盖 src，不检查散放在 mod 目录的运行时 Java，也不发布 JAR。
- build 用 JDK 17 执行 Maven clean package，默认备份并更新 MociShipPack 工作区 JAR；--no-deploy 仅打包到 target。用户确认本次游戏发布后，才可加 --game-approved 同时同步游戏 JAR。
- verify 从 src、主 mod 的 data/com、游戏原版 data 和 pom.xml 的 systemPath JAR 查类，检查 wpn/system/modPlugin、船插/能力声明和受支持 CSV。找到源码只证明存在声明，不证明游戏已成功编译加载。可多次传 --file 缩小到本次改动；不擅自修无关文件。
- logscan 优先读绑定游戏 starsector-core/starsector.log，按 Java 包与内部类定位工程、mod 或原版源码。
- 无响应诊断优先保留 JFR/线程栈证据；`logscan` 只能定位已经写入日志的异常，不能替代对卡死线程的采样。
- sync --file <工程相对路径> 可重复列出本次资源；默认只展示计划，不写游戏。向用户询问并获得本次清单确认后，才加 --game-approved 执行备份与同步，保留游戏目录其他文件。
- api-src/api-grep 可直接读本地 starfarer.api 目录；find-class 也查运行时源码。javap 适用于已有字节码，不代表查看了游戏实际加载的类。
- new 默认只预览；--write 只创建预先核对过的全新文件，Java 进入 src，数据进入 MociShipPack。CSV/JSON 接线根据 Moci 实际格式合并，不自动追加模板行。

根据改动选择已有测试或必要的新测试。编译只能证明源码可编译，静态接线检查只能覆盖列明的引用；UI、战斗行为与任务流仍需针对性验收。仅修改本 skill 时，发布链在隔离目录测试，避免把用户尚未交付的 mod 改动发布出去。

## 发布

先完成工作区：配置与资源以 MociShipPack 为准，src/ Java 修改后默认 build 更新工作区 JAR，散放 Java 保持在 MociShipPack 原位置。任何写入游戏目录的动作都需要用户明确确认本次范围；此前默认自动同步的授权已被此偏好替代。询问前先给出可核对的文件清单、验证结果及目标目录，不让用户批准尚未准备好的修改。

确认后同步工具核对两个 mod 的顶层 ID 为 moci_shippack，并验证游戏目标位于绑定游戏的 mods 内。--game-approved 仅记录已有的本次用户确认，不能自行添加代替询问。游戏运行时停止游戏同步；不自动关闭或启动游戏。工作区构建与更新不依赖游戏是否运行。

旧 JAR 备份和发布收据放工程 .work/MociShipPack/backups/。同步失败会尝试恢复本次覆盖；回滚也失败时必须报告具体目标与备份路径，不能声称发布成功。

资源同步按环境参考的单独规则执行，不整包覆盖、不删除游戏目录其他内容。测试期间只在临时工程演练文件发布。

## 收尾

说明行为变化、实际运行的检查、JAR/资源是否同步、需要用户实机验证的内容。复杂功能按需留设计与关键问题记录；不强制每次产出 HANDOFF/CASE 或让用户先确认才记录已完成的工作。

最终回复末尾按 SKILL.md 的“收尾文件清单”列出本次新增、修改、替换、重命名或删除的实际文件，提供可点击路径与简短用途，并关联构建/游戏同步状态；修改 skill 本身时也执行这一规则。
